# Data

## What the dataset is

Real Booking.com data for Tokyo, 10–17 September 2026, 2 adults, 1 room, EUR, captured once
on 2026-08-13 through the Booking.com MCP connector and committed as a versioned fixture in
`src/travel_intel/data/fixtures/tokyo_2026-09-10_2026-09-17/`.

It lives *inside* the package rather than beside it, so it travels through wheels, containers
and hosted deployments. Resolving it relative to the repository root worked under an editable
install and broke everywhere else.

| File | Records | Captured by |
|---|---|---|
| `accommodations.json` | 30 unique properties | 3 searches: `Shinjuku, Tokyo`, `Asakusa, Tokyo`, `Tokyo, Japan` filtered to 4–5 stars |
| `activities.json` | 27 unique products | 3 searches, one per provider category: `food_drinks`, `museums_arts_culture`, `nature_outdoor` |

Three searches rather than one, because a single query returns ten near-identical mid-range
properties. The captured spread is **€70–€646 per night** (€490–€4,526 for the stay), which
is what makes a price model meaningful rather than decorative.

Every record carries `Provenance.SNAPSHOT`. Nothing in this repository is synthetic, and
nothing generated by a model is stored as if it were a retrieved fact.

## Decisions made at capture time

The fixture is a **projection** of the provider payload, not a verbatim dump. Each choice is
recorded in the fixture's own `notes` block so it can be audited without reading this file:

- **`price.book` is the total for the stay, not a nightly rate.** The adapter divides by
  `nights` in exactly one place. Reading it as a nightly rate would have put a Setagaya
  apartment at €333/night and silently wrecked every budget calculation downstream.
- **Amenities are filtered to a 26-item whitelist.** The raw lists are dominated by COVID
  cleaning protocols and fire-safety boilerplate, identical across properties and therefore
  worthless as features. The whitelist is stored in the fixture.
- **URLs are stripped of query strings**, which carried an affiliate id and the search
  parameters.
- **Missing means missing.** One property has no rating at all and several activities have
  zero reviews; both are stored as `null`. Imputing 0 would turn "we do not know" into "it
  is terrible" — the ranking treats those cases through `data_completeness` instead.

## Known limitations of the data

These are real constraints on what the system can honestly claim.

1. **No maximum occupancy.** The endpoint does not expose it. Every record was returned by a
   search for 2 guests, so capacity is enforced *by the provider at retrieval time*, and the
   adapter sets `max_occupancy = searched_adults` rather than guessing higher. A request for
   4 travellers against this snapshot raises a warning instead of a fabricated answer.
2. **Activities have no coordinates** and often no address. Hotel-to-activity distance
   therefore cannot be computed, and the ranking does not pretend to use it. `location` in
   the ranking means distance to Tokyo Station, derived from real coordinates.
3. **Provider category tags are noisy.** A Golden Gai bar-hopping tour is returned by the
   `nature_outdoor` search. The noise is preserved rather than hand-corrected: hiding it
   would hide a genuine data-quality problem that a text classifier over titles and
   descriptions is the proper fix for.
4. **No duration per activity.** Itinerary planning uses one documented default
   (`DEFAULT_ACTIVITY_HOURS = 3.0`) instead of inventing per-product durations.
5. **Prices are a single point in time** for a single stay length and party size. Any request
   that diverges from the captured query produces an explicit warning
   (`RetrievalResult.warnings`) rather than a silently invalid number.
6. **30 properties is a small training set.** The price model is a demonstrative model with
   honest error bars, not a production estimator. See `docs/evaluation.md`.

## Refreshing the snapshot

Re-run the three accommodation searches and the three category searches with the same
parameters (`checkin 2026-09-10`, `checkout 2026-09-17`, 2 adults, 1 room, EUR, locale
`en-us`), project the payload through the documented rules above, and bump `captured_at`.
Keep `schema_version` in step with any field change so the loader fails loudly on a
mismatch instead of half-reading an old capture.

`user_locale` matters: a Spanish locale returns amenity names and product titles in Spanish,
which would silently break the amenity whitelist.
